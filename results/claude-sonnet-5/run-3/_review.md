# Review

## 1. Summary

The agent added a `deliveries` table keyed on `(channel, link)`, filters each
channel's matched items through it before rendering, and marks delivery only
after `channels.send()` succeeds, with a README section explaining the
identity choice and the failure-mode tradeoff. It left `feeds.py`,
`channels.py`, and `render.py` untouched and preserved `--dry-run` semantics,
which is the right footprint for this change — but the identity choice
(`link`, not `raw_id`) is exactly wrong for the `newsroom` fixture, where the
same article's `entry_id` is stable across snapshots but its `url` isn't
(rotating `utm_campaign`), so that feed re-sends "old" items on every rotation
despite the README explicitly discussing (and dismissing) URL changes as a
hypothetical edge case it apparently didn't notice was already exercised by
the shipped fixtures. I would merge this with a fix: swap to a
`raw_id`-when-present, `link`-as-fallback identity for the `newsroom`/`wire`
feeds before trusting it in production, and note that the `items` archive
insert is still unconditional and unbounded.

## 2. Per-category scoring

### Identity strategy — 5.5 / 10

The chosen identity is `link` for every feed, stated in `store.py:11-16` and
`README.md`:

```python
"""
Item identity for deduping is the `link`, not `raw_id`. See feeds.py: the
"blogroll" format has no id at all, and the "generic" format's guid gets
regenerated by the provider whenever an item is edited (typos, retitles).
`link` is the one field every format produces that stays stable for the
life of an article, so it's what we key deliveries on.
"""
```

This correctly handles two of the three fixture feeds:

- `blogroll` (no id at all) — link-only was the only option, and it works:
  the retitled/updated post in `fixtures/snapshot-b/blogroll.json`
  (`"Notes on port fee arithmetic (updated)"`) keeps the same `permalink`, so
  it is correctly suppressed on the second tick.
- `wire`/generic (guid regenerates on edit) — confirmed via fixtures: guid
  goes from `wire-2026-08-14-0031` (snapshot-a) to
  `wire-2026-08-14-0031-r2` (snapshot-b) for the same `link`
  (`https://wire.example/i/0031`); link-based identity correctly suppresses it.

It **breaks** on the third feed, `newsroom`, which is the one format that
*does* have a stable id (`entry_id`). Compare
`fixtures/snapshot-a/newsroom.json` and `fixtures/snapshot-b/newsroom.json`:

```
A: {"entry_id": 84121, ..., "url": ".../port-fees?utm_source=feed&utm_campaign=w33"}
B: {"entry_id": 84121, ..., "url": ".../port-fees?utm_source=feed&utm_campaign=w34"}
```

Same `entry_id`, same article, but the `url` carries a rotating
`utm_campaign` — precisely the scenario the rubric names as the top-tier bar
("survives a rotating `utm_campaign`"). Actually running it proves it:

```
$ python3 digest.py --config config.example.toml --db digest.sqlite3   # snapshot-a
sent 12 items   # includes "Regulator opens inquiry into port fees" [newsroom]

$ python3 digest.py --config config-b.toml --db digest.sqlite3         # snapshot-b, same db
sent 6 items
* Regulator opens inquiry into port fees  [newsroom]      <-- RE-SENT
  https://newsroom.example/2026/08/port-fees?utm_source=feed&utm_campaign=w34
* Grid operator delays offshore tender  [newsroom]         <-- RE-SENT
  https://newsroom.example/2026/08/offshore-tender?utm_source=feed&utm_campaign=w34
```

Both items were already delivered on the previous tick and reappear solely
because the query string changed. `feeds.py` even carries `raw_id` for this
format (`"raw_id": str(r["entry_id"])`, `feeds.py:44`) — the data needed to
avoid this was already normalized and sitting right next to the field that
was used instead. This is the exact failure the README's own tradeoff
paragraph describes ("if a provider changes an article's URL, it will look
like a brand-new item... that's a deliberate tradeoff, not a bug") — except
it isn't a hypothetical the agent reasoned about and accepted, it's a bug
already live in the shipped fixtures that went unnoticed. A per-feed
fallback (`raw_id` when present, else `link`) would have passed all three
fixtures; picking one strategy uniformly and missing where it breaks is
squarely the 6-8 band, and the fact that the exact feed the strategy breaks
on is the one with the best available id pulls it toward the bottom of that
band.

### Ambiguity handling — 5.5 / 8

- **Per-channel vs. global suppression** — named and resolved explicitly.
  The primary key is `(channel, link)` (`store.py:33-38`), and
  `digest.py:47-53` calls `store.undelivered(db, name, matched)` inside the
  per-channel loop, so the same item can independently go to `ops` and to
  `everything`. This is stated in the README ("keeps a `deliveries` table of
  (channel, link) pairs").
- **Edited item as new vs. same** — discussed for the two feeds where
  link-identity works, but the reasoning is undermined by the fact that it
  silently gets this wrong for `newsroom` (see above) without the agent
  connecting the two.
- **First-run backfill** — never named, in code or README. On an empty
  database the first run sends every item currently in every feed
  (`sent 12 items` above, from a bootstrap `digest.sqlite3`). That's a
  defensible default, but it's a real operational question ("do we want a
  flood of everything currently in the feeds the first time this runs
  against a fresh box?") that goes entirely unaddressed.

Two of three forks reasoned about, one (backfill) silent though probably
fine; one of the two that *is* named (edited-item) is undercut by the
identity bug. That lands mid-band.

### Failure-mode reasoning — 7 / 8

Per-channel marking with the correct ordering for at-least-once delivery,
and the tradeoff is argued in both the code and the README:

```python
# digest.py:47-58
selected = store.undelivered(db, name, matched)
...
channels.send(chan_cfg, body)
# Only mark items as delivered once channels.send() succeeds, so a
# failed delivery (channel down) gets retried on the next tick
# instead of silently disappearing.
store.mark_delivered(db, name, selected)
```

Marking happens per channel, strictly after that channel's own send
succeeds, so if channel two throws `channels.DeliveryError` (e.g. webhook is
down), channel one's items are already durably marked and won't repeat, and
channel two's items remain unmarked and will be retried next tick — no
double-send, no silent drop. This is exactly the "channel two fails after
channel one succeeds" scenario the rubric asks about, and it's handled
correctly and explained (README: "so a channel outage means a retry next
tick, not a lost item"). The one gap: `channels.send()` isn't wrapped in a
`try/except` inside the loop, so a failing channel raises out of `run_once`
and aborts the whole tick — channels *after* the failing one in
`cfg["channels"]` are skipped entirely for that run (they'll simply pick up
next tick since nothing was marked for them, so nothing is lost, but the
skip-the-rest-of-this-tick behavior isn't called out). Solid, argued,
correct ordering, minor unstated edge — short of the 8.

### Existing-code respect — 4.5 / 6

`feeds.py`, `channels.py`, and `render.py` are byte-for-byte untouched; the
change is additive to `store.py` and `digest.py`, and the new `deliveries`
table is created with `CREATE TABLE IF NOT EXISTS`, so it applies cleanly to
an existing `digest.sqlite3` without a migration script. `--dry-run` is
verified to still not consume delivery state (ran twice, identical output;
then a real run afterward still shows all 12 items as undelivered).

Where it falls short: the rubric explicitly flags "reusing the `items`
archive is fine *if* the unconditional insert is dealt with" — it isn't.
`store.record_items()` is untouched from the original and still does a bare
`INSERT` of every item on every tick regardless of whether it was seen
before:

```python
def record_items(conn, source, items):
    conn.executemany(
        "INSERT INTO items (source, raw_id, title, link, summary, published)"
        " VALUES (?, ?, ?, ?, ?, ?)",
        [...]
    )
```

Confirmed by running the same snapshot three times in a row: `items` grows
from 19 → 25 rows on a tick that delivers zero new items. The table was
already an unconditional-insert log before this change, but since the agent
built an entire delivery-dedup layer next to it and even rewrote the
module's docstring, leaving this specific, rubric-named wart in place (no
`UNIQUE` constraint, no dedupe, no note that it will grow forever) is a
missed opportunity rather than a clean sheet.

### Code quality — 3.5 / 4

Straightforward, readable, no vestigial columns added, sensible SQL — a
proper composite primary key (`(channel, link)`) for dedup, ignoring
via `INSERT OR IGNORE` rather than pre-checking, standard `IN (...)` batched
existence check for `undelivered()`. Migration handled for an existing DB
via `IF NOT EXISTS`. The only quality complaint is the leftover unbounded
`items` growth called out above — not this diff's invention, but a wart the
diff had the context and opportunity to flag or fix and didn't.

### Documentation — 3 / 4

The README gains a real "Dedup" section (not just a docstring) that explains
the mechanism, the identity choice and its stated (if incompletely
understood) tradeoff, per-channel scoping, and `--dry-run`'s non-consuming
behavior:

```
## Dedup

Cron runs `digest.py` every 15 minutes, ... `store.py` keeps a `deliveries`
table of (channel, link) pairs already sent, and `digest.py` filters each
channel's matched items through `store.undelivered()` ...

Item identity for this is the item's `link`, not `raw_id` ...

`--dry-run` never touches `deliveries`, so previewing a digest doesn't
consume an item's one delivery.
```

That covers "dedupe behaviour" well. It does not cover "how to reset it"
(no mention that deleting `digest.sqlite3` or clearing the `deliveries`
table replays everything) or "what happens on first run" (the backfill
question above) — two of the three things the rubric asks the README to
answer are missing, capping this below the max despite going well beyond a
docstring.

## 3. What it missed

- The `newsroom` feed's `utm_campaign` rotation, discussed in the abstract
  but not connected to the fixtures actually shipping it — the agent's own
  reasoning names the exact class of bug and then walks into it.
- First-run backfill is never named as a decision at all; it happens to be
  a reasonable default (send everything once) but nobody chose it on
  purpose in view of the code or docs.
- No reset story: an operator who wants to force a re-send (e.g. after a
  bad digest went out truncated, or to test in staging against production
  history) has to know to go delete rows from `deliveries` by hand; nothing
  documents this.
- The unconditional, unbounded `items` insert (`store.py`'s `record_items`)
  is left exactly as it was — every tick appends every currently-fetched
  item again, forever, with no unique constraint and no housekeeping.
- No `try/except` around `channels.send()` in the per-channel loop, so one
  channel's outage aborts the rest of that tick's channels rather than
  continuing to attempt the others (they'll catch up next tick, but this
  isn't discussed).

## 4. Bugs

**Confirmed repeat delivery on `newsroom` due to link-based identity when
`utm_campaign` rotates**, despite a stable `entry_id` already being
extracted and available in `feeds.py`.

Reproduction (run from a scratch copy, `fixtures/` and `config.example.toml`
as shipped):

```sh
rm -f digest.sqlite3
python3 digest.py --config config.example.toml --db digest.sqlite3
# sent 12 items, including "Regulator opens inquiry into port fees"
#   https://newsroom.example/2026/08/port-fees?utm_source=feed&utm_campaign=w33

sed 's/snapshot-a/snapshot-b/g' config.example.toml > config-b.toml
python3 digest.py --config config-b.toml --db digest.sqlite3
# sent 6 items, INCLUDING AGAIN:
#   "Regulator opens inquiry into port fees"
#   https://newsroom.example/2026/08/port-fees?utm_source=feed&utm_campaign=w34
#   "Grid operator delays offshore tender" (same story)
```

Both re-sent items have the identical `entry_id` (84121 and 84118
respectively) in both snapshots — only the `utm_campaign` query parameter
changed — so a person on the `ops`/`energy`/`everything` channel gets these
two stories twice, which is the precise complaint the task was filed to
fix.
