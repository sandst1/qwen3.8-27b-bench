# Review — claude-sonnet-5, run-4

## 1. Summary

The agent added a `notified` table keyed on `(source, dedupe_key)`, computed
a per-feed-format `dedupe_key` in `feeds.py` that survives each fixture's
specific instability (rotating `utm_campaign`, missing id, regenerated
`guid`), and wrote it all up carefully in `README.md` and inline comments.
The identity strategy is genuinely good and verified correct against both
fixture snapshots, but the implementation marks items "notified" for *all*
channels before any channel has actually been sent to, and does not catch
per-channel delivery exceptions — so a single failing channel (e.g. one dead
webhook) crashes the run and permanently drops the item for every channel,
including ones that hadn't been reached yet and ones later in the loop. I
would merge this after fixing that one ordering bug; the rest of the design
is sound and well-documented.

## 2. Per-category scoring

### Identity strategy — 9.5 / 10

`feeds.py` computes a distinct `dedupe_key` per format, with the failure
mode for each format spelled out in the module docstring:

```python
# feeds.py:10-21
`dedupe_key` is what digest.py uses to decide "have we already notified
someone about this item", and it is deliberately *not* always `raw_id`:

  * newsroom's `entry_id` is stable across polls, but its `url` carries a
    `utm_campaign` param that changes every week — so we key on raw_id.
  * blogroll has no id field at all, but `permalink` is stable even when
    the title/excerpt get tweaked after publishing — so we key on link.
  * generic's `guid` gets regenerated by the provider whenever an item is
    edited (typo fixes, retitles, added tags), which would make an edited
    item look "new" and re-trigger a notification — its `link` is the
    stable part, so we key on link too.
```

I ran both fixture snapshots through the pipeline (`snapshot-a` then
`snapshot-b`, same sqlite db) to check this against the actual data rather
than just the docstring:

- `newsroom` entry `84121` keeps `entry_id` but its `url` gains
  `utm_campaign=w34` (was `w33`) between snapshots → correctly **not**
  re-sent.
- `blogroll`'s "Notes on port fee arithmetic" gets a title/excerpt edit
  (`"(updated)"`, corrected table) between snapshots, `permalink` unchanged
  → correctly **not** re-sent.
- `wire`'s guid changes from `wire-2026-08-14-0031` to
  `wire-2026-08-14-0031-r2` (provider re-issues on edit), `link` unchanged →
  correctly **not** re-sent.
- The genuinely new `newsroom` item (`entry_id 84130`) in snapshot-b is
  correctly sent.

This is exactly the three-scenario stress test the rubric's top band
describes, and it holds. Docked half a point only because the identity
choice for `blogroll`/`generic` (keying on `link`) means a genuine
same-content republish under a new URL would be silently treated as a new
item — an edge case not discussed, but not one the fixtures exercise either.

### Ambiguity handling — 6 / 8

Two of the three canonical forks are named and resolved explicitly with
reasoning; the third is decided silently (though reasonably).

**Per-channel vs. global suppression** — named and resolved, in both a code
comment and the README:

```python
# digest.py:45-54
# Mark these as notified once they've been through the pipeline for
# this run, *not* only the ones that ended up matching a channel.
# Otherwise an item that doesn't match any channel's keywords today
# would stay "unnotified" forever and get re-evaluated every 15
# minutes; if someone later widens a channel's keywords it would
# suddenly show up as a "new" item for something that's actually
# old news. --dry-run must not mark anything, or a real run right
# after it would silently skip items nobody was ever sent.
if not dry_run:
    store.mark_notified(db, feed_cfg["name"], new_items)
```

The choice made — suppression is global per-source, not per-channel — is
reasonable (it avoids the "widen keywords, old news reappears" surprise) but
it is exactly the choice that produces the failure-mode bug below: since
marking isn't tied to per-channel delivery, it happens whether or not
delivery to any given channel actually happened.

**Edited item as new vs. same** — named and resolved (see identity strategy
section above; `feeds.py`'s docstring and the README's "Deduplication"
section both walk through why an edit shouldn't count as new).

**First-run backfill** — not mentioned anywhere. On an empty `notified`
table, the very first invocation will treat every item currently in every
feed as "new" and blast the entire backlog to every matching channel in one
digest. That's a defensible default, but it's undocumented and the agent
never says "and here's what happens the first time you run this against a
live feed." Since the rubric requires all three forks to be *identified*
for the top band, and this one isn't mentioned at all, this caps the score
at the "one or two named" band.

### Failure-mode reasoning — 2.5 / 8

This is the weak point. `run_once` marks items notified once per feed,
**before** the channel-delivery loop even starts:

```python
# digest.py:32-69
def run_once(cfg, db, dry_run=False):
    all_items = []
    for feed_cfg in cfg["feeds"]:
        ...
        new_items = store.unnotified(db, feed_cfg["name"], items)
        all_items.extend(new_items)
        ...
        if not dry_run:
            store.mark_notified(db, feed_cfg["name"], new_items)   # <-- marked here

    all_items.sort(key=lambda i: i.get("published", ""), reverse=True)

    sent = 0
    for chan_cfg in cfg["channels"]:                                # <-- delivery starts here
        selected = [i for i in all_items if matches(i, chan_cfg)]
        if not selected:
            continue
        body = render.digest(selected, chan_cfg)
        if dry_run:
            print(f"--- would send to {chan_cfg['name']} ---")
            print(body)
            continue
        channels.send(chan_cfg, body)                               # <-- can raise, uncaught
        sent += len(selected)

    return sent
```

`channels.send` (`channels.py:17-38`) raises `DeliveryError` on webhook
failure and that exception is never caught in `digest.py` or `main()` — it
propagates and kills the process (`digest.py:74-89`, no try/except around
`channels.send`). `channels.py`'s own docstring states the intended
contract:

```python
# channels.py:1-6
Delivery is best effort: if a channel is down we let the
exception propagate and cron will pick us up again on the next tick.
```

But by the time that exception is raised, `mark_notified` has already run
for every feed. I reproduced this: with three channels where the second
(`energy`, webhook) points at a closed port, the run crashes after printing
`ops`'s digest but before `energy` or `everything` ever run — yet all items
from all three feeds are already in the `notified` table. A follow-up run
with a working config against the *same* database sends 0 items: the
`energy` channel's tender/grid/offshore items, and the entire `everything`
firehose digest, are gone forever, not retried on the next cron tick as the
docstring promises. This is the rubric's "partial-failure window that loses
... a whole batch" case almost exactly. There is no per-channel marking, no
transaction/rollback tying the mark to actual delivery, and no discussion
anywhere of what a mid-run crash does to already-marked-but-undelivered
items.

### Existing-code respect — 5.5 / 6

The change is additive and respectful of what was there. `feeds.py` keeps
`raw_id` untouched and only adds `dedupe_key` alongside it; `store.py` keeps
the original `items` archive table and its stated "nothing reads it" purpose
completely unchanged, explicitly calling that out:

```markdown
The original `items` table is unchanged: it's still a pure archive of
everything ever seen (keyed by autoincrement id, not dedupe_key), for
"did this ever come through?" questions. It plays no part in suppressing
repeats.
```

`--dry-run` is preserved and explicitly extended to never mark items
(`digest.py:53`, `if not dry_run:`), with the reasoning given in the same
comment block. No wholesale rewrites, no scope creep (no scheduler, no
config format changes, no plugin system). Docked half a point for not
touching the failure-mode implications of the design it built on top of.

### Code quality — 3.5 / 4

Clean, minimal SQL, sensible schema, no dead code, no vestigial columns:

```python
# store.py:31-36
CREATE TABLE IF NOT EXISTS notified (
    source      TEXT NOT NULL,
    dedupe_key  TEXT NOT NULL,
    notified_at TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (source, dedupe_key)
);
```

`mark_notified` uses `INSERT OR IGNORE`, correctly handling the
already-marked case without raising on the primary-key collision
(`store.py:74-79`). `unnotified` builds a parameterized `IN (...)` query
rather than string-interpolating values (`store.py:60-71`) — no injection
risk. `CREATE TABLE IF NOT EXISTS` handles the schema addition for an
existing database without a separate migration step, which is adequate for
this scale. Docked half a point because there's no `db_version`/migration
guard at all — fine today, but the "handled for an existing database" bar
in the rubric implies slightly more than "the CREATE happens to be
idempotent."

### Documentation — 2.5 / 4

The README gained a substantial "Deduplication" section (`README.md:33-66`)
explaining the `dedupe_key` rationale per feed and the general shape of the
`notified` table. It does not, however, address two things the rubric
explicitly asks for: how to reset the dedup state (there's no mention of
deleting rows from `notified`, or of what wiping the sqlite file does), and
what the very first run against a live feed will do (blast the entire
current backlog to every channel at once — see ambiguity handling above).
Since it's well above "docstring alone" but silent on two of the three
required topics, it lands in the middle of the band rather than the top.

## 3. What it missed

- **First-run backfill** is never named. A brand-new deployment (or a
  restored/reset db) will send the entire current feed backlog as a single
  digest the first time it runs — not obviously wrong, but never discussed,
  and it's the kind of thing an on-call person would want to know before
  their first cron tick pages three channels at once.
- **Reset instructions**: nothing in the README says how to force items to
  be re-sent (e.g., `DELETE FROM notified WHERE source = ...`) if a channel
  needs a manual re-notify.
- **Delivery-vs-marking ordering**: the core bug — see Failure-mode
  reasoning and Bugs.
- **No retry granularity smaller than "the whole feed for this run"**: even
  ignoring the crash bug, there's no way to re-notify a single channel that
  had a transient failure without either editing the db by hand or
  re-running before `mark_notified` fires for that feed (which isn't
  exposed as an option).

## 4. Bugs

**Marking happens before delivery, and delivery exceptions are uncaught —
items are permanently lost when a later channel fails.**

Reproduction (using the fixtures, snapshot-b, 3 channels where the middle
one is a webhook to a closed port):

```
$ python3 digest.py --config config-fail.toml --db digest-fail.sqlite3
=== ops ===
Ops digest — 4 item(s)
...
Traceback (most recent call last):
  ...
channels.DeliveryError: energy: <urlopen error [Errno 61] Connection refused>
$ echo $?
1
```

Inspecting the db immediately after the crash shows every item from every
feed already marked notified:

```
$ sqlite3 digest-fail.sqlite3 "select source, dedupe_key from notified"
newsroom|84130
newsroom|84121
newsroom|84118
blogroll|https://blog.example/port-fee-arithmetic
blogroll|https://blog.example/offshore-tender-history
wire|https://wire.example/i/0031
wire|https://wire.example/i/0918
```

Re-running against the *same database* with a healthy, all-`stdout` config
(simulating "cron picks us up on the next tick," which is the explicit
contract stated in `channels.py`'s own docstring) sends nothing:

```
$ python3 digest.py --config config-retry.toml --db digest-fail.sqlite3
sent 0 items
```

The `energy` channel's tender/grid/offshore items, and the `everything`
channel's entire digest for this poll, never went out and never will — the
crash happened before either of those channels ran, but the items were
already marked as notified before the channel loop even started. This
directly contradicts the "cron will pick us up again on the next tick"
guarantee documented in `channels.py:1-6`.
